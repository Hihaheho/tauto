# ビルド時間の計測

`tauto build` の `--timings` は工程ごとの経過時間を人が読む表として、
`--timings=json` は機械が読む一行の JSON として、標準エラーの最後に出す。
どちらも成果物のパスを出す標準出力と終了コードを変えない。指定しなければ
時計を読まず、計測の出力も作らない。`run` は受け付けず、生成したプログラムの
実行時間は計らない。両方の指定、繰り返し、未知の形式は使用法のエラーになる。

JSON の前には通常の診断や信頼する extern の一覧があり得る。標準エラー全体が
JSON 文書なのではなく、**最後の一行が計測のレコード**である。引数が有効で
ビルドを開始した場合に限り、成功時にも通常のエラー時にもレコードを出す。
使用法のエラー、パニック、強制終了についてはレコードを保証しない。
レコードの書き込み失敗はビルドの成功・失敗を変えない。

## 工程の境界

時間は単調な時計の壁時計時間で、CPU 時間ではない。他の処理との競合、ファイルの
読み書き、子プロセスを待つ時間も含む。引数の検査を終えた後からビルドの結果を
返す直前までを計る。プロセス起動、引数の検査、構文の探索ディレクトリの設定、
計測レコード自身の整形・出力は含まない。

工程は入れ子でなく実行順の連続区間である。各区間はその境界から次の境界までを
含み、間の制御処理、局所的なデータの破棄、通常の診断も直前の工程に属する。
成功時の成果物パスの出力とビルド全体のデータの破棄は `finish` に属する。
工程同士の重なりはなく、工程時間の和が全体時間になる。全体時間を工程時間に
足してはならない。工程をさらに分けた内部処理の CPU 費用を表すものではない。

| 工程 | 含む処理 |
| --- | --- |
| `input` | 入力の判別、マニフェスト、一つのソースファイルの読み込み |
| `tote_load_check_extract` | tote の依存・import・include の読み込み、解析・展開、証明検査、実行可能な宣言の抽出と連結を行う API |
| `parse_expand` | 構文解析、マクロ・クラスの展開、名前解決を行う解析 API |
| `check` | 型、effect の行、所有権・使用回数の検査と prelude の準備 |
| `lower` | 検査済みプログラムから NIR への変換 |
| `codegen` | 出力名、Rust の binding 解決と生成ワークスペースの構築 |
| `write` | Rust の生成ファイルの内容比較と書き込み |
| `codegen_write` | JavaScript の binding・特殊化・宣言・ホストコードの生成とファイル書き込み。Rust wasm extern の生成と書き込みも含む |
| `native_compile` | Cargo の起動と完了待ち、コンパイラ診断の解釈 |
| `finish` | 成果物パスの出力とビルド全体のデータの破棄 |

解析 API の内部では展開と名前解決が結び付いているため、それぞれを独立の
計測値としては出さない。tote の読み込み API は証明検査と抽出も行うため、
それらを含む `tote_load_check_extract` を一つの工程として計る。その後の
`parse_expand` と `check` は抽出された実行可能なプログラムに対する処理であり、
証明検査の別計測値ではない。単一ファイルでは tote の工程を作らない。ランタイムの
実行工程も作らない。`--emit rust` は Cargo を起動しない。JavaScript の node と
browser はモジュールを出すだけで、Rust extern がある場合だけ wasm の Cargo
ビルドを計る。その前後の `codegen_write` は別々の区間として並ぶ。

正常終了では到達した全工程が `ok` になる。通常のエラーでは最後の工程だけが
`failed` になり、到達しなかった工程は並べない。失敗した工程の時間はエラーを
返すまでの時間で、工程を完了したという意味ではない。

## JSON の形式

レコードの `schema_version` は整数 `1`、`kind` は `tauto.build.timings`。
`backend` は `rust` または `javascript`、`target` は `host`、`node`、`browser`。
`status` は `ok` または `failed`、`duration_ns` は全体のナノ秒数。
`phases` は実行順の配列で、各要素の `name`、`duration_ns`、`status` は工程名、
ナノ秒数、工程の状態を示す。同名の工程が複数あっても上書きしない。
期間の整数は非負の 64 bit で、表現範囲を超える期間は最大値に飽和する。

`cache.native` は `not_run` または `unknown`。Cargo を起動する境界に達した場合は
`unknown` であり、起動失敗も含む。Cargo の通常出力からキャッシュの命中を
推測しない。`cache.proof` も `not_run` または `unknown` で、tote の読み込み境界に
達した場合に `unknown` となる。証明キャッシュの利用方針や命中・不命中の件数は
その API からは分からない。`unknown` を不命中として集計してはならない。

`cache.generated_sources` は観測できなければ `null`。Rust の生成ファイルの
書き込みが成功したときは `provenance` が `content_equality`、`hits` が既存内容と
一致して書き込みを省いたファイル数、`misses` が書いたファイル数となる。
これは生成ソースの再利用であり、コンパイラの成果物や証明キャッシュの命中率では
ない。書き込み途中の失敗について部分的な件数を成功件数として報告しない。
JavaScript の出力ファイルについてはこの再利用を観測しない。Rust wasm extern の
生成ワークスペースについては Rust の生成ファイルとして観測する。

レコードは入力パス、ソース、環境変数、依存の URL、エラーメッセージを含まない。
通常の診断の内容は変えない。形式の利用者は `schema_version` を確認し、未知の
フィールドを無視する。整数の時間や工程の状態を使い、表示用の表を解析しない。

## 検査

レコードの区間・全体・失敗の関係は、実時間に依存しない明示した時計の値で
検査する。CLI の検査は指定なしとの標準出力・終了コードの一致、診断に続く JSON、
生成ファイルの再利用、入力・検査・書き込み・Cargo のエラー、ネイティブの
成果物、JavaScript の両ターゲットを扱う。時間の絶対値には期待値を置かない。
