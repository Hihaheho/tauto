# 上限付きのキューバッチ

有限の待機キューから、指定件数までの先頭ジョブを取り出す。送信先の件数制限に合わせた
バッチ作成を想定する。同じジョブ ID が二度現れたときも、その二つを勝手にまとめない。
既存の状態遷移例とは異なり、ここで扱うのは一つの不変なキュースナップショットの分割だけである。

## 仕様と前提

`pending` は有限の `List(A)`、`limit` は自然数である。`batch_items(limit, pending)` は
先頭から上限まで、`batch_remaining(limit, pending)` はその後ろを返す。二つの呼出しには
**同じスナップショットと同じ上限**を渡す。

- バッチと残りを順に連結すると、元のリストと一致する。順序と重複回数もそのままである。
- バッチの長さは上限を超えない。
- 元の件数が上限以上なら、バッチは上限ちょうどの長さになる。
- 元の件数が上限以下なら、バッチは元のリスト全体になる。
- 上限ゼロでは何も取り出さず、残りは元のキューである。繰り返し消費する呼出し側は正の上限を使う。
- 正の上限と空でないキューなら先頭を消費する。空キューは空のままである。

ID の一意性、外部キューの更新、送信、ack、再試行、永続化、並行実行はモデルに含めない。
この分割は exactly-once 配信の保証ではない。計算資源、スタック、メモリの上限も保証しない。

## 実装と証明の対応

`src/batch.taut` の二つの実装は、標準ライブラリの `List::take` と `List::drop` を呼ぶ。
同じファイルの定理は、その**実装関数そのもの**を参照する。証明専用の別実装は置かない。

| 要件 | 検査する定理 |
|---|---|
| 順序・重複を含めて元に戻る | `batch_reassembles` |
| 上限を超えない | `batch_size_bounded` |
| 足りるときは上限まで詰める | `batch_fills` |
| 短い末尾も取り出す | `batch_short_queue` |
| ゼロは一時停止として扱う | `batch_zero_keeps_queue` |
| 正の上限で先頭を消費する | `batch_positive_consumes_head` |

`src/main.taut` は、同じ関数を呼ぶ小さな実行ドライバーである。重複を含むキュー、
二回に分けた消費、空、ゼロ、残件数より大きい上限を実行する。具体的な出力と期待値は
`cases/check/bounded-batch.eure` に置く。`checks_all = "ok"` は追加の公理なしでの検査を要求する。

## 再現

リポジトリのルートで実行する。CLI の準備には Rust の固定ツールチェーンと依存の取得、
JavaScript の実行には Node が必要である。

```sh
cargo build --locked -p tauto-cli --bin tauto
TAUTO_BIN="$PWD/target/debug/tauto" bash scripts/check-bounded-batch.sh
```

スクリプトは CLI をビルドし直さない。fresh な証明検査、source bundle の出力と
`--axiom-free` での再検査、eval・Rust・JavaScript・VM の順での実行を行い、四つの出力を
互いに、さらに具体的な期待値と比較する。いずれかの失敗、バックエンドの欠落、出力の
違いは失敗となり、skip や別バックエンドでの代用はしない。開始時と終了時の pure source bundle、
ドライバー、manifest の一致も確認する。検査中はソースを編集しない。

最初に表示する一時ディレクトリに、bundle、検査結果、各出力、工程ごとの秒数を残す。
Rust と VM の初回実行ではバックエンド用のビルドが必要になる場合があり、冷えた状態の
所要時間とキャッシュ済みの再実行は同じではない。実測値はその実行の `seconds.tsv` を使う。
これはこの例だけの検査で、workspace 全体の合格を意味しない。

trust 境界の回帰検査は、次のコマンドで個別に実行できる。

```sh
cargo nextest run --locked -p tauto-cli --test bounded_batch
```

ケースランナー全体の検査には `cargo nextest run --locked -p tauto-test-suite` を使う。
これはこの例に限定した短時間の検査ではない。

## 何を信用するか

source bundle の entry は `src/batch.taut` である。実装と定理、その相対 import の閉包と、
使用する標準ライブラリのソース・ハッシュ・宣言レポートを持つ。再検査は元の checkout がない
ディレクトリから行い、保存された「成功」という主張ではなくソースと証明を検査する。
同じ実行ファイルのバイト列での再検査が必要であり、受取側はその実行ファイルを別途信用する。
ハッシュは整合性の検査であって、署名・作者認証・再現可能ビルドの証明ではない。

**証明済みなのは純粋なソース関数の定理である。** カーネル、標準 prelude、抽出、最適化、
Rust/JavaScript/VM のバックエンドとランタイムはこの例では証明しない。四経路の一致は具体的な
入力に対する回帰検査であり、すべてのプログラム・入力についてのコンパイラー正当性の証明ではない。

`src/main.taut`、パッケージ manifest、生成コード、バイナリは source bundle の対象外である。
ドライバーが違う上限を渡したり、返された残りを使わずジョブを捨てたりすれば、純粋な関数の証明が
通ってもアプリケーションは誤る。CLI の回帰検査は二つの境界を区別する。

- 実際の `batch_items` を「上限に関係なく全件返す」に変え、ハッシュを計算し直しても、証明の
  再検査が拒否する。レポート改変とハッシュ不一致も拒否する。
- ドライバーだけが違う上限を渡す変更は、pure bundle の検査を通るが、実行出力が変わる。
  これは呼出し側が証明対象でないことを可視化する検査である。

bundle の詳細は [`docs/design/trust-bundles.md`](../../docs/design/trust-bundles.md) にある。
